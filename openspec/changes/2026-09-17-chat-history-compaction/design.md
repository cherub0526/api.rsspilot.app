## Context

2026-09-17 評估 OpenRouter 的 token 成本時發現的：chat 每一輪都重送整段歷史。當時量到的實際數字（dev DB，7 筆有內容的摘要 + 實際模板）：

| 區塊 | 字元數 | 估算 tokens |
|---|---|---|
| assistant system prompt（不含摘要） | 1,779 | ~450 |
| 摘要 `long_summary.content`（中位數） | 2,382 | ~1,600 |
| 每輪對話（估） | — | ~500 |

換算：一題的 input 約 2,000 tokens（system + 摘要），歷史每多一輪加約 500。

## Goals / Non-Goals

**Goals:**
- 讓送進推論的歷史長度**由 server 決定且有上限**
- 上限可線上調整，不必重新部署
- 保留「接續追問」的可用性（最近幾輪必須是原文）

**Non-Goals:**
- 改變 API 的請求／回應形狀
- 動到 `chat_messages` 的既有資料（前端的歷史列表照舊讀完整紀錄）
- 改變每日額度規則

## Decisions

### 1. 滑動視窗優先於滾動總結

20 輪對話的三種做法：

| 做法 | 累計 input | 額外請求 | 相對現況省下 |
|---|---|---|---|
| 現況（全歷史） | ~135,000 | — | — |
| 滾動總結（每 5 輪一則） | ~85,000 + 總結 4 次（~11,000 in / 1,200 out） | 4 | ~40,000 tokens |
| **滑動視窗（最近 10 輪）** | ~90,000 | **0** | ~35,000 tokens |

省下的 40,000 tokens 在 low 帶是 **$0.0026**、medium 帶是 **$0.047**——一整段對話省不到五分錢。滑動視窗拿到其中約九成，代價是零額外請求、零新失敗模式。

**判準**：總結多出來的那一成效益，要用一支 job、一張新資料、一個新 prompt、一個競態條件去換。在有實際用量數字之前，這個交換不成立。

### 2. 這個產品截斷歷史的品質代價比一般 chatbot 低

參考資料（影片摘要）放在 **system prompt 每輪重送**，不在歷史裡。丟掉早期輪次，使用者失去的只是「對話自己的線索」，不會失去影片內容。一般 chatbot 不敢截斷是因為知識只存在歷史裡；這裡不是。

### 3. 輪數門檻放 `configs` 資料表，不放 `config/ai.php`

Swoole 是常駐程序，改 env／config 要重啟整個 server 才生效。會來回試的值一律放資料表——這是 `OpenRouterModels` 當初把模型對照表放進 `configs` 的同一個理由。

### 4. 階段 3 採「單一滾動總結 + 最近 N 輪原文」

每 N 輪（預設 5）壓縮一次，而且**永遠只有一則總結**：新一批 N 輪不是另外產生一則，而是
連同現有的那則一起重寫成新的一則。

```
第 1–5 輪 ：[原文 ×5]
第 6 輪   ：[總結 S1(1–5)] + [原文 ×1]
第 10 輪  ：[總結 S1(1–5)] + [原文 ×5]
第 11 輪  ：[總結 S2 = f(S1, 第 6–10 輪)] + [原文 ×1]
第 16 輪  ：[總結 S3 = f(S2, 第 11–15 輪)] + [原文 ×1]
```

送進推論的歷史因此是**定值**：一則總結（上限固定）+ 最多 N 輪原文，與對話總長度無關。
這是這個設計相對於「每 N 輪各留一則總結」的關鍵差別——後者的總結會線性累積
（50 輪 ≈ 10 則 ≈ 3,000 tokens），前者不會。

代價是**遞迴壓縮的失真**：第 1 輪的內容在第 51 輪時已經被壓縮過 10 次。緩解方式是把
總結的 prompt 寫成「更新」而不是「重寫」——輸入既有總結與新的 N 輪，輸出仍是同一份結構
（例如條列的事實／已下的結論／使用者的偏好），明確要求保留數字、名詞與結論原樣。

這個產品能接受這種失真是有前提的：**影片摘要在 system prompt 每輪重送**，總結只需要記住
「問過什麼、得到什麼結論」，而不必扛住影片內容本身。

### 5. 總結存在 `chat_sessions`，而且它是快取不是真相

單一總結讓儲存位置不必再三選一：`chat_sessions` 加兩個欄位即可。

| 欄位 | 用途 |
|---|---|
| `summary` | 目前這一則總結的文字 |
| `summary_through_message_id` | 這則總結涵蓋到哪一則訊息（ULID，含） |

`chat_messages` **一列都不會被刪**，所以：

- 前端的歷史列表完全不受影響，使用者看到的仍是完整逐輪紀錄
- 總結壞掉（或 prompt 改版）時可以從原文重算，代價是 N 分之一次的呼叫
- `historyOf()` 的組法是「`summary` + `summary_through_message_id` 之後的所有訊息」，
  沒有總結時就是全部原文——退化行為自然成立

### 6. 失敗路徑也必須有上限

這個功能的目的就是「歷史不會無限長大」，所以**總結失敗時的退路不能是無限長的原文**。

job 連續失敗、或還沒跑完就來了下一輪時，`historyOf()` 會退回「總結 + 其後全部原文」，
而那一段會隨著失敗次數一直長。必須加一道硬上限：未壓縮的原文超過 2N 輪時，直接丟掉最舊的、
只保留最近 N 輪（等同於階段 2 的滑動視窗）。**壞掉的 job 最多讓對話失憶，不能讓帳單失控。**

### 7. 壓縮的競態：同一 session 只能有一個在跑

總結是 `f(舊總結, 新的 N 輪)`，兩支 job 同時對同一段對話做壓縮會互相覆蓋（各自讀到同一份
舊總結、各自寫回不同的新總結，後寫的贏，中間那批輪次就永久遺失）。

兩道防線都要：

1. job 用 `ShouldBeUnique`，`uniqueId` 綁 session
2. 寫回時以 `summary_through_message_id` 當樂觀鎖——只有「目前的值仍等於我讀到的那個」
   才寫入，否則整批放棄（下一輪會再觸發一次）

注意殘留鎖的既有坑：`ShouldBeUnique` 的鎖在 worker 被 SIGKILL 時不會釋放，之後的 dispatch
會靜默消失（見 `docs/lore/transcription/pitfalls.md`）。這裡的後果不嚴重——壓縮沒發生就是
退回原文，`uniqueFor` 到期後自然恢復——但要知道會這樣。

### 8. 其餘三件仍然成立

1. **快取每 N 輪斷一次。** 前綴是 `system(含摘要，~2,000 tokens)` → `總結` → `原文` →
   `本輪提問`。system 那一段不變、永遠命中；總結被改寫的那一刻，它之後的整段失效。
   換句話說每 N 輪有 1 輪付全額 input + cache write。
2. **總結必須非同步，而且不計使用者額度。** 第 N 輪回答完就派 job 先算好，第 N+1 輪才不用
   等。它是一次真實的 OpenRouter 請求、吃帳號的 20 RPM，但使用者沒問這一題，不該扣點。
3. **最近 N 輪永遠是原文。** 最常見的追問是「你剛剛說的那個數字」。「剛好第 N 輪」那一刻
   不能連最近一輪都換成總結——上面的時間軸因此是「壓縮完成後原文從 1 輪重新累積」，
   不是「壓縮後只剩總結」。

### 9. 階段 1 的接縫已經在位

`ChatController::historyOf()` 是唯一產生歷史的地方，回傳 `[{role, content, images}]`。階段 2 在這裡加 `limit`，階段 3 在這裡改成「總結 + 尾段原文」，兩者都不必動 `buildMessages()` 以下的任何東西。

## Open Questions

- 壓縮門檻 N 預設 5（使用者指定），視窗上限若只做階段 2 則建議 10
- 總結本身的長度上限是多少？它是唯一不受輪數限制的成長來源，必須有明確的字數／token 目標
  寫進 prompt，否則「更新總結」會一次比一次長
- 實際的 session 長度分布如何？**這決定階段 3 值不值得做，目前沒有資料**——若九成的對話
  不到 5 輪，這套機制永遠不會被觸發
- 視窗要以「輪」還是「token」計？輪數好懂、token 才真的對應成本
